# Dependency Review: ESLint 9 to 10

## Summary

- Date: 2026-08-25
- Scope: move off the deprecated ESLint 9 line, and repair the overrides that
  the move made wrong.

## Classification

- Elevated-risk. A major upgrade of the lint toolchain, a two-major jump of the
  React hooks plugin, and four `overrides` changes affecting what resolves.

## Why

Every ESLint 9 release is deprecated upstream — *"This version is no longer
supported"* — including `9.39.5`, which carries the `maintenance` dist-tag.
There is no supported patch to move to; the line is end-of-life. Found by
`pnpm candidate` while adding lint to the SDK, on a condition that had been
sitting in the client unnoticed.

## Targets

| Package | From | To |
|---|---|---|
| `eslint` | 9.36.0 | **10.8.1** |
| `@typescript-eslint/parser` | 8.45.0 | **8.67.0** |
| `@typescript-eslint/eslint-plugin` | 8.45.0 | **8.67.0** |
| `eslint-plugin-react-hooks` | 5.2.0 | **7.1.1** |
| `eslint-plugin-react-refresh` | 0.4.22 | **0.5.4** |

`eslint-plugin-react-hooks` had to cross two majors: the earliest release
declaring `eslint ^10` is **7.1.0**. Neither 5.x nor 6.x supports ESLint 10, so
the jump is mandatory rather than opportunistic.
`@typescript-eslint/eslint-plugin` moves only to stay in lockstep with the
parser; the flat configs never load it, so those settings remain inert.

## Release Age

**The age gate did real work here, for the first time.** The intended targets
were `latest`: `eslint@10.9.1` and `@typescript-eslint/parser@8.68.0`, both
published **the same day** and both failing the seven-day gate. Backed off to
the newest releases that clear it:

| Target | Published | Age |
|---|---|---|
| `eslint@10.8.1` | 2026-08-07 | 17 d |
| `@typescript-eslint/parser@8.67.0` | 2026-08-10 | 14 d |
| `eslint-plugin-react-refresh@0.5.4` | 2026-08-10 | 14 d |
| `eslint-plugin-react-hooks@7.1.1` | 2026-04-17 | 129 d |
| `minimatch@10.2.6` | 2026-07-27 | 28 d |

The gate is not advisory: `minimumReleaseAgeStrict` would have failed the
install regardless.

## Advisory Review

`pnpm candidate` on the eligible set: **exit 0, 20 packages examined, nothing
needing a decision.** No install scripts anywhere. `eslint` has two advisories,
neither affecting 10.8.1; the other three have none.

`pnpm audit` after the upgrade is unchanged: one finding, `elliptic` (low),
unpatchable, accepted.

The tree **shrank**: 862 packages to 849, with 17 leaving. ESLint 10 dropped
dependencies, including `@eslint/eslintrc` entirely.

## The React Compiler rules, and why they are not adopted

Plugin v7 changed what `recommended-latest` means. Enabling the upgrade with the
config untouched took lint from green to **223 errors** — none of them
`rules-of-hooks`:

| Rule | Client | SDK |
|---|---|---|
| `set-state-in-effect` | 74 | 20 |
| `immutability` | 57 | — |
| `refs` | 33 | — |
| `static-components` | 13 | — |
| `purity` | 9 | — |
| `use-memo` | 5 | 4 |
| `preserve-manual-memoization` | 4 | — |
| `set-state-in-render` | 3 | — |
| `void-use-memo` | 1 | — |

All nine are new React Compiler rules. **`rules-of-hooks`, the rule we actually
gate, reports zero in both packages.**

So both configs now **enumerate the rules they gate** instead of spreading
`reactHooks.configs['recommended-latest'].rules`. Adopting 223 violations as a
side effect of a security-motivated upgrade would fold a large code-quality
decision into a supply-chain fix — the exact conflation this policy exists to
prevent. The rules are left unlisted rather than explicitly disabled, so no rule
name that exists only in v7 is pinned.

Verified the surviving rule is live rather than assumed: reintroducing a
conditional `useState` into `ErrorModal.tsx` fails lint with
`react-hooks/rules-of-hooks` and exits 1; reverting it exits 0.

## Source / Upstream Review

**The upgrade made three overrides wrong, and revealed a fourth already stale.**
This is the liability pattern already recorded for `@hpke/core`: an override
that pins a transitive *below* where its parent is heading becomes harmful the
moment the parent moves.

| Override | Parent now declares | Action |
|---|---|---|
| `eslint>minimatch: 3.1.4` | `^10.2.5` | **removed** |
| `@eslint/config-array>minimatch: 3.1.4` | `^10.2.4` | **removed** |
| `@typescript-eslint/typescript-estree>minimatch: 9.0.7` | `^10.2.2` | **removed** |
| `@eslint/eslintrc>minimatch: 3.1.4` | parent gone from the tree | **removed** |

Left in place, ESLint 10 would have run on a minimatch seven majors older than
it asks for. Lint happened to work, which is precisely why this needed checking
rather than trusting a green result.

Removing them is safe because the declared ranges cannot reach a vulnerable
version: minimatch's advisories patch at 10.2.1 and 10.2.3, and `^10.2.5` starts
above both. `copyfiles>minimatch`, `glob@7.2.3>minimatch` and
`glob@10.5.0>minimatch` are retained — those parents genuinely still need the
older lines.

One override **added**: `minimatch@10.2.6>brace-expansion: 5.0.9`. minimatch 10
declares `^5.0.8`, and **5.0.8 is itself an affected version** (patched 5.0.9),
so the declared range alone is not safe. Same shape as the existing 3.x and 9.x
pins. Verified in the lockfile: `eslint@10.8.1 -> minimatch: 10.2.6 ->
brace-expansion: 5.0.9`.

## A workflow gap the gate exposed

The install was **blocked by `.pnpmfile.cjs`** — correctly, on
`eslint-plugin-react-refresh@0.5.4` not being in the reviewed set. That is the
resolution gate working in anger for the first time.

But it exposed a documented gap: the reviewed set is derived from the lockfile,
and the lockfile cannot update while the install is blocked. The way through is
to resolve once with `PISTOLS_ALLOW_UNREVIEWED=1`, account for the diff, then
regenerate. `docs/dependency-reviews/README.md` now documents that sequence,
along with the honest limit it implies: the guarantee is **not** "nothing
unreviewed is ever fetched", but that nothing unreviewed is fetched without a
deliberate, auditable act.

## A tool bug fixed on the way

`candidate.mjs` reported that `zod@3.25.76` "does NOT satisfy
`^3.25.0 || ^4.0.0`". It does. `satisfies()` had no disjunction handling, so the
range was unevaluable, and the report printed unevaluable as unsatisfied — a
false statement, in the tool built to stop false statements.

Range evaluation now uses the reviewed `semver@7.8.5` already present in the
dependency graph, resolves dist-tags separately, and distinguishes unevaluable
input from a definite mismatch. Retained Node tests cover disjunctions,
comparators, zero-major carets, tags, exact versions and npm aliases.

## Lifecycle Scripts

None of the five targets, and none of the new arrivals, carries an install
script. `allowBuilds` unchanged.

## Commands Run

```sh
node scripts/candidate.mjs eslint@10.9.1 ... --depth 1        # age gate FAIL, backed off
node scripts/candidate.mjs eslint@10.8.1 ... --depth 1        # exit 0
PISTOLS_ALLOW_UNREVIEWED=1 pnpm install
node scripts/lockfile-diff.mjs
pnpm exec turbo lint                                          # 223 errors, then 0
node scripts/generate-reviewed-set.mjs --record docs/dependency-reviews/2026-08-25-eslint-10.md
pnpm install && sh scripts/verify.sh
```

## Outcome

- Off the deprecated ESLint line, on a supported toolchain.
- Lint green in both packages, with the gated rule proven live.
- Four wrong or stale overrides removed, one added for a range that permits an
  affected version.
- Tree smaller by 13 packages. Reviewed set 1,025 to 1,010.
- `pnpm verify` green, and the resolution gate passes without the bypass.

## Follow-ups

- **223 React Compiler violations** are now a known, measured backlog, on top of
  the 342 `exhaustive-deps`. `set-state-in-effect` (94 across both packages) and
  `immutability` (57) look the most likely to be hiding real bugs. Worth taking
  one rule at a time.
- `eslint@10.9.1` and `@typescript-eslint/parser@8.68.0` become age-eligible
  around 2026-08-31. No reason to rush them.
- `@typescript-eslint/eslint-plugin` is installed and never loaded; the client
  config sets three of its rules inertly. Tidy alongside the dependency-removal
  work.
