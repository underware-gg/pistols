# Starknet / Dojo.js / React Rubicon Migration

## Objective

Move the client and published SDK together from React 18, Starknet.js 8 and
Dojo.js 1 to React 19, Starknet.js 10 and Dojo.js 2 without deploying production
or changing the on-chain world schema.

The validated starting point is `wip/rob` at `d00a4d9f`. GitHub CI and both
Vercel preview projects passed for that exact commit. Work remains on
`wip/rob`; `main`, remote `dev`, Sepolia and mainnet are not migration targets.

## Decisions already made

| Area | Decision |
| --- | --- |
| Cairo world | Stay on Dojo 1.8.0 and the current Scarb/Sozo/Katana/Torii line. Dojo.js 2 is a client-library major, not an instruction to migrate the deployed world. |
| Starknet ID | Remove `starknetid.js`. Preserve the existing hooks using Starknet.js 10's built-in `getStarkName`, `getAddressFromStarkName` and `getStarkProfile` support. |
| React connector | Replace `@starknet-react/*` and unscoped `get-starknet-core` with `@starknet-start/*` and scoped `@starknet-io/get-starknet-*` packages. |
| Semantic UI React | Retain it for this migration. Admit React 19 only through narrowly scoped compatibility rules and observed interaction tests. Do not perform an 80-file UI rewrite. |
| Published SDK | The migrated release is `@underware/pistols-sdk` 2.0.0. React 19, Starknet 10 and Dojo.js 2 peer changes are consumer-breaking. Do not publish during migration work. |
| React Compiler rules | Defer until the platform migration is complete. Re-measure the backlog under React 19 before choosing rules to adopt. |

## Non-goals

- Replacing Semantic UI React.
- Changing Cairo models, events, systems, world seed or deployed world data.
- Running `./migrate sepolia`, `./migrate mainnet` or any production deployment.
- React Router 8, Vite 8, TypeScript 7 or a Node runtime-floor migration.
- Clearing the React Compiler backlog while platform behaviour is moving.
- Preserving React 18 or Starknet 8 compatibility in SDK 2.0.

## Phase 0 — reproduce the current binding baseline

This is the only prerequisite before crossing the dependency boundary.

1. Install the versions already pinned in `.tool-versions`:
   Scarb 2.13.1, Sozo 1.8.7, Katana 1.7.1 and Torii 1.8.16.
2. Confirm `asdf current` reports all four as installed from this checkout.
3. Run the current Cairo build and tests with no dependency changes.
4. Start isolated local Katana and Torii services and run the dev migration with
   TypeScript binding generation.
5. Compare the regenerated manifest, constants and TypeScript bindings with the
   committed files.

Exit criteria:

- `sozo build` and `sozo test` pass on the current pins.
- A local dev world can be migrated and indexed.
- Binding and constants generation completes.
- Generated output is clean, or any pre-existing drift is understood and
  resolved separately before the Rubicon begins.
- No remote chain or production branch has changed.

Completion evidence — 2026-08-28:

- The four pinned tools are installed and reported by `asdf current`.
- `sozo build` passes. The first 667-test run reported 653 passing, two failing
  and 12 intentionally ignored tests. Both failures were swapped
  `should_panic` wrapper expectations in the duelist sacrifice tests, not
  contract behaviour; after correcting them, the complete five-test sacrifice
  slice passes.
- A second unrestricted full-suite run was stopped after it proved too
  CPU-intensive for a local workstation. Exhaustive Cairo reruns are delegated
  to CI unless explicitly approved; migration work uses changed-area filters.
- `./migrate dev --bindings` deployed the unchanged world to isolated local
  Katana. Local Torii indexed it and returned a concrete duelist through
  GraphQL. Neither remote chain nor a production branch was touched.
- The manifest and constants regenerated byte-identically. Sozo 1.8.7's known
  invalid TypeScript shapes are now corrected by a fail-closed, idempotent
  postprocessor at the binding-generation boundary. SDK and client builds,
  lint, and their 52 combined tests pass with the regenerated output.

## Phase 1 — review the complete candidate graph

Run the repository's exhaustive `pnpm candidate` workflow before editing any
manifest. Review the coupled set together:

- React, React DOM and their 19.x types.
- Starknet.js 10 and the direct RPC types package.
- `@dojoengine/core`, `@dojoengine/sdk` and `@dojoengine/utils` 2.x, plus every
  changed Dojo transitive.
- Cartridge Controller and Connector 0.14.
- `@starknet-start/react` and its chains, explorers, providers and query family.
- Scoped get-starknet core, modal and wallet-standard packages.
- Any Semantic UI compatibility resolution, including `react-is` if the React
  19 tests require it.

For every arrival, record the exact selected version, publication age,
advisories, deprecation, required and optional peers, lifecycle scripts and
browser-bundle relevance. Create the dependency review record before changing
the manifests.

Exit criteria:

- The complete graph has passed the release-age and advisory policy, or an
  explicit documented decision exists.
- Required peers and lifecycle-script decisions are known.
- No candidate has entered the manifest, lockfile or pnpm store through an
  accidental install.

## Phase 2 — cross the package boundary once

Update the coupled package graph as one resolution change. Do not advance its
members piecemeal.

- Move React, Starknet.js, Dojo.js and Cartridge to the reviewed targets.
- Add the reviewed `@starknet-start/*` and scoped get-starknet packages.
- Remove `@starknet-react/*`, unscoped `get-starknet-core` and
  `starknetid.js` when their call sites have moved.
- Update exact catalog pins and the SDK's published peer ranges independently:
  exact versions for this tree, compatible 2.0 consumer ranges for peers.
- Resolve once through the documented reviewed-set workflow, inspect the full
  lockfile diff, then admit the reviewed versions.

Exit criteria:

- Strict peer resolution and frozen installation pass.
- There is one React runtime and one Starknet 10 runtime in the client/SDK
  graph. The verifier-only `starkscan` CLI may retain its isolated legacy
  Starknet dependency.
- No old connector or Starknet ID package remains accidentally reachable.

Type errors are expected while call sites are being migrated; they are not an
acceptable final checkpoint.

## Phase 3 — migrate the stable client boundaries

### Wallet and provider layer

- Move provider composition, connectors, hooks, chains and explorer utilities
  from `@starknet-react/*` to `@starknet-start/*`.
- Adapt the existing Controller and predeployed connectors to the new request,
  account and RPC types rather than leaking two connector models through the
  SDK.
- Preserve application-level wallet behaviour: reconnect, connect, disconnect,
  chain selection, account changes and transaction submission.

### Starknet ID boundary

- Keep the public hook surface in `sdk/src/utils/hooks/useStarkName.ts` stable.
- Replace `StarknetIdNavigator` with Starknet.js 10 provider methods.
- Preserve query keys, loading/error behaviour and returned profile fields.
- Add behaviour tests for forward lookup, reverse lookup and profile lookup.

Exit criteria:

- Both packages typecheck.
- Wallet/provider tests pass without wholesale mocks of the dependency being
  verified.
- Starknet ID no longer appears in manifests, lockfile or published peer types.

## Phase 4 — migrate Dojo.js and regenerate bindings

- Adapt SDK initialization, provider composition, queries, subscriptions,
  entity decoding and system execution to Dojo.js 2 APIs.
- Regenerate TypeScript bindings from the unchanged local Dojo 1.8 world.
- Treat generated differences as evidence: inspect model, event, contract and
  calldata shape changes before updating consumers.
- Do not change Cairo schemas merely to make a client type error disappear.

Local integration proof must exercise:

- Initial entity query and model decoding.
- Live subscription update through Torii.
- One system execution through a local account.
- Controller or predeployed connector connect/disconnect behaviour.
- Manifest and world-address configuration.

Exit criteria:

- Generated files are reproducible with the pinned toolchain.
- Local Katana/Torii read, subscription and write paths work.
- No on-chain schema migration has been introduced.

Completion evidence — 2026-08-28:

- `./migrate dev --bindings` rebuilt the unchanged Cairo world in 18 seconds,
  migrated it to isolated local Katana, regenerated bindings through the
  fail-closed postprocessor, and left the manifest and constants unchanged.
- `pnpm --filter @underware/pistols-sdk test:local-dojo2` initializes the
  Dojo.js 2 SDK against local Torii, decodes `pistols-Config`, observes a live
  subscription update, executes `admin.set_paused` with the local prefunded
  account, and restores the original value. The command exits successfully
  after cancelling the subscription.
- The wallet-standard predeployed connector test proves connect, chain ID,
  request and disconnect behaviour. No remote world or Cairo schema changed.

## Phase 5 — prove Semantic UI under React 19

Use the smallest compatibility accommodation supported by observed behaviour.

1. Add package-scoped peer allowances only for the React-18-capped packages
   actually present in the resolved Semantic UI graph.
2. Verify Semantic UI's `react-is` usage against React 19 elements. Prefer a
   package-scoped React 19 resolution or a minimal maintained patch if the
   installed React 18 copy misclassifies them.
3. Check React 19's `element.ref` warning on Portal-backed components. Patch the
   boundary if it affects behaviour or leaves actionable warnings in normal use.
4. Add interaction tests for:
   - Modal open, close, portal and focus behaviour.
   - Dropdown mouse and keyboard selection.
   - Popup trigger and dismissal.
   - Representative Form, Menu and Button rendering.

Exit criteria:

- Strict installation passes only through named, documented exceptions.
- The interaction tests pass under React 19.
- The tested paths do not emit unaccounted React compatibility warnings.
- Any future Semantic UI replacement remains a separate project.

Completion evidence — 2026-08-28:

- Peer exceptions are exact and package-scoped to the abandoned Semantic UI
  graph.
- A pnpm patch replaces the two Portal `element.ref` reads with React 19's
  `props.ref` path in source, ESM and CommonJS artifacts.
- Four interaction tests cover the representative primitive layer, Dropdown
  selection, Popup hover/dismissal and Modal portal/Escape dismissal. They pass
  under React 19 without compatibility warnings.

## Phase 6 — make the SDK 2.0 contract honest

- Set the SDK release line to 2.0.0 without publishing it.
- Update peer ranges and exported types for React 19, Starknet 10, Dojo.js 2,
  Cartridge 0.14 and `@starknet-start/*`.
- Remove obsolete peers and compatibility aliases whose retirement condition is
  met.
- Add concise consumer migration notes covering renamed packages, peer floors
  and any changed exported types.
- Pack the SDK and install that tarball into an isolated consumer fixture using
  the supported peer set. Typecheck and run a minimal import/provider smoke test.

Exit criteria:

- The packed SDK contains no workspace-only or stale React 18/Starknet 8
  assumptions.
- A clean consumer resolves exactly one compatible peer set.
- The package is ready to publish later, but no registry publish has occurred.

Completion evidence — 2026-08-28:

- Root, client and SDK release lines are `2.0.0`; the SDK was not published.
- `pnpm test:sdk-package` packs the SDK into a temporary clean consumer,
  installs the supported exact peers, typechecks public imports, runs a runtime
  smoke test, and proves one React, Starknet and Dojo SDK runtime.
- Consumer migration notes record the renamed packages, wallet connector shape,
  Starknet ID replacement, and the two narrowly scoped Starknet Start rules.

## Phase 7 — full branch and preview validation

Run the complete gate and observe the application rather than treating a build
as sufficient evidence.

- `CI=true pnpm verify`.
- Clean frozen install from a fresh dependency tree.
- Full local Katana/Torii integration proof.
- Production-mode client build and bundle comparison against the baseline.
- Push `wip/rob`; require GitHub CI to pass for the exact commit.
- Require both Vercel preview projects to deploy that commit successfully.
- Exercise the preview's connect, wallet/profile lookup, query/subscription and
  representative Semantic UI paths.

Exit criteria:

- Worktree and remote `wip/rob` agree on the verified commit.
- CI, public preview and authenticated prerelease preview pass.
- No push or merge to `main`, no push to remote `dev`, and no production or
  remote-world deployment has occurred.

Local completion evidence — 2026-08-28:

- Frozen install, reviewed-lock checks, advisories, production builds,
  typechecks, lint and all JavaScript/TypeScript tests pass locally.
- The clean SDK consumer fixture and full local Katana/Torii integration proof
  pass.
- Remote CI, Vercel previews and browser observation remain deliberately
  pending until this work is committed and the user authorizes a push.

## Commit checkpoints

Keep failures attributable without pretending the coupled dependency graph can
be split into independent upgrades:

1. Toolchain baseline evidence and any baseline-only generated correction.
2. Candidate review record.
3. Coupled dependency graph plus migrated provider/connector boundary.
4. Starknet ID replacement and its tests.
5. Dojo.js client/binding migration and local integration proof.
6. Semantic UI React 19 accommodation and interaction tests.
7. SDK 2.0 contract and consumer fixture evidence.
8. Final verification-only corrections.

Each code checkpoint should build, typecheck and pass its relevant tests before
the next concern is layered on. A temporary failing state may exist inside a
checkpoint, not at handoff.
